# ADR 0022 — Remove from the list: a view filter in nika's own state

Date 2026-11-20 · Status accepted (nika 0.5.4, RM; owner answers 2026-11-19: RM-Q1 A, RM-Q2 A, RM-Q3 A)

## Context
- **Rows the user cannot clear.** nika lists every Claude Code session it finds, grouped by folder. A folder that is "Not a nika project" (a scratch folder, a test harness, a worktree) stays in the dashboard for as long as it has sessions in the window, and so does a session that ended long ago or one that is live with no tmux pane nika sees (stuck, or running in a tmux server nika does not read). The user has no way to take such a row off the list.
- **They count.** A stuck session that waits for the user raises the tray's attention count and the dashboard's "Waiting on you", so a row the user no longer cares about keeps asking for attention.
- **nika must not delete or stop anything for this.** Nothing under Claude's folder or in a project is nika's to remove (rules 4 and 11), and nika never signals a process. `claude rm` (deleting a session) was considered and not built.
- **Constraints.** Rule 9: every file nika's own folders hold is agent-writable, so a stored label or path would be a display string an agent can write. Rule 5: no path comes from a request. Rule 10: the browser tier on :3335 gets no new data of substance.

## Decision
- **A view filter, not a deletion.** The app tier stores which rows are left out of the lists. Nothing is deleted, signalled or changed in Claude's folder or in a project. **The copy says so:** "Removed items are only hidden from nika's lists. Nothing was deleted, and sessions that still run keep running."
- **The store: `<state>/hidden.json`, version 1.** `{ v: 1, sessions: { <session id>: { at } }, groups: { <folder key>: { at } } }`. It holds ids, folder keys and times, and no name, path or label: the "Show removed" list takes names and paths from nika's own fresh snapshot, never from the file. Session ids are UUIDs, folder keys match `PROJECT_KEY` (the key of the group in nika's own snapshot), and `at` is a safe integer in `[0, now + 1 day]`. The file is read through `src/fsafe.js` (a regular single-link file of the user, at most 64 KiB), parsed strictly, and a bad entry is ignored with one warning while a bad file is ignored as a whole with one warning, so a read **fails open**: rows show. 500 entries at most across both maps (newest kept), which is about 30 KB by construction; an entry older than 90 days stops applying and is dropped by the next write. Every write prunes (rule 11, `src/fwrite.js`: 0600 file in a 0700 folder, one write after another in one promise chain). A `readHidden` that gets an `env` that is not a plain object reads nothing, so a test or an old caller can never reach the real state folder.
- **Two kinds of entry.**
  - *A session entry* hides one row. It is offered for every row that is not live in a tmux pane nika sees: ended rows, and live rows with no pane (stuck). A row in a tmux pane always shows (End session stays its way out). A session entry is dropped by the next write while the session runs in a tmux pane.
  - *A folder entry with a start-time watermark* hides a **detected** folder (never a nika project, never the `(unknown)` group). A row of the folder is left out only when the folder is not a nika project, the row is not live in a tmux pane nika sees, **and the row started at or before the Remove** (`startedAt`, else the last activity, `<= at`). So a **new** session in that folder brings the folder back with only the new rows; the old rows stay removed (owner answer RM-Q1 A), and an old row shows only while it runs in tmux. A group that is not a nika project and has no visible row is dropped from the groups of the snapshot; its rows still count in `hidden`.
- **Every view reads it; control paths do not.** The filter applies to `GET /api/agents` on **both tiers**, the tray line and `nika status`. Pane eligibility, `orchestrators()` and the saved-orchestrator state, a pane's repo key, `findSession` / `findSessions`, spawn limits (tmux tags) and the session page by URL read the **unfiltered** data. A filtered snapshot would make a running saved orchestrator read "ended" and offer Resume. So the app tier keeps the unfiltered snapshot for its controls and builds a filtered one for the status tick.
- **Routes (app tier only, behind the `/api/app/*` guard, never on :3335)**, in the new `src/hidden-routes.js`: `POST /api/app/session/:id/remove` and `…/unhide`, `POST /api/app/groups/:key/remove` and `…/unhide`, `GET /api/app/hidden`. A write body is exactly `{}`. `:id` must be a UUID that `findSession` resolves to that very row; `:key` must be a group of nika's own snapshot (or already stored), looked up by key whatever the age of its sessions (an index-only walk of the transcripts when the 7-day snapshot has no such folder). Errors: 404 for an unknown or malformed target, 409 `in-tmux` for a row with a pane, 409 `registered` for a folder that is a nika project, 503 `index_unavailable`, 500 `write_failed` (nothing written). Unhide takes any well-formed id or key, since it can only shrink the file.
- **What the browser tier gets: counts only.** Every group and the snapshot gain `hidden: <number>`; no id, key or time reaches :3335. `nika status` prints one line, "… 3 removed from the list (Show removed in the nika app)". There is no new CLI command.
- **A cache that follows a write.** The server keeps a snapshot for 1.5 s; `hiddenGeneration()` goes up after every successful write in the process and a cache entry made under another generation is a miss. The app tier's own refresh after a Remove or Undo is therefore fresh; the browser tier catches up within its cache TTL.
- **UI.** A detected folder's header menu and a row's `⋯` menu carry **Remove from the list** (app tier only). One click, no confirm, a toast with **Undo** for 10 s. A line on the dashboard and the project page opens **Show removed**: two sections, folders then sessions, newest first, at most 100 each, each with **Show again**. A removed folder older than the recent snapshot still shows its label and path (the list reads them in one index-only walk per request), and "Removed 3 min ago" / "just now" survives the time refresh. The list is fetched again after every Show again or Undo while the dialog is open.
- **Not built:** `claude rm` and any End or SIGTERM half (owner answer RM-Q2 A); a note on the session page; the `(unknown)` group's folder Remove.
- **Rule text.** Rules 4, 5, 6, 10 and 11 carry the `hidden.json` reads and writes, the display text and the counts-only line (RM-Q3 A).

## Alternatives
- **Per-session ids only for a folder:** breaks once a session leaves the window nika lists, and past the 500 cap. A folder entry with a watermark is one entry and still lets a new session in.
- **Store labels or paths in the file:** an agent can write the file, so what the page shows would be an agent-writable display string (rule 9). The file holds keys and the labels come from nika's own index.
- **A page-only filter:** not applied on :3335, in the tray or in `nika status`.
- **Filter the snapshot everywhere, controls included:** hides a running saved orchestrator from the controls that start, resume and gate it (T69).
- **Any use brings the whole folder back with all its rows (RM-Q1 B), or nothing comes back automatically and only rows in a tmux pane show (RM-Q1 C):** both were offered; the owner chose A.
- **`claude rm` (RM-Q2 B):** offered and not chosen (owner answer RM-Q2 A: hide only). It would act on sessions and worktrees outside nika's own state.

## Consequences
1. **T67 to T71** (`docs/security.md`). A process of the user can edit `hidden.json` to hide rows or fill it with junk; the read fails open, a row in a tmux pane always shows, a nika project is never hidden as a folder, and the count line and Show removed make every removal visible (single-user model, rule 10). A request cannot name something nika did not detect or smuggle a path (T68). Hiding does not change what nika controls (T69). A removed session keeps running out of sight (T70). A cached list after a write, two writes racing, and an oversized file are covered by the generation counter, the write chain and the cap (T71).
2. **Residual rows of the comeback table.** (a) An old row of a removed folder that is resumed in tmux shows while it runs there and disappears again when it ends. (b) A folder that is added as a nika project and removed again within 90 days is hidden again, because its entry is kept and applies again. Both were accepted.
3. **A removed session that waits for the user in another terminal is no longer announced** by the tray (T70). It still shows in the "Removed" count and in Show removed, and it shows again the moment it runs in a tmux pane nika sees.
4. **A session in a private tmux server** (the isolated live-check harness, or `tmux -L`) has no pane nika lists, so it is "stuck", offered Remove, and stays removed. The live check recorded a related limit: a foreign pane id that equals one of nika's own panes is taken for it (pre-existing, not RM's).
5. **Costs.** A Remove of a folder whose sessions are older than 7 days waits for one index-only walk of the transcripts. Undo or Show again of one entry can drop other entries whose sessions run in a pane right now (the approved write-time prune); the answer does not tell the page how many.
6. `docs/contracts/api-app.md` (the five routes and the snapshot counts), `docs/security.md` (T67 to T71) and `docs/design/spec.md` (§9.24: the menu entries, the toast, Show removed) carry the details.
