# ADR 0021 — Agent placement: an 80 × 15 floor, the parent's window, `agents` windows, and no split into a fitted window

Date 2026-11-20 · Status accepted (nika 0.5.4, P1 and the small-fix round; replaces the owner decision "Spawn gives the window back first" of ADR 0017)

## Context
- **The squeeze.** `beside` was `split-window -h -t =<session>:`. tmux resolves that to the active pane of the session's current window, so every spawn halved whatever pane was active, and a few agents later each pane was a few columns wide. `under-last` and an explicit `under` had no floor either.
- **The contract and the code disagreed.** The contract says "beside that parent", but `=<session>:` is the session's current window, not the parent's. A sub-orchestrator's agents landed beside the main orchestrator instead of beside their parent.
- **The Fit release only covered the app.** ADR 0017 had `spawn` give a fitted window back before a split (`releaseFitted`, `fit.releaseWindow`). The CLI has no fit controller, and orchestrators spawn through `nika spawn`, so the release protected only a spawn made from the app. An orchestrator's spawn could still split a window that was zoomed and sized to a panel.
- **Constraints.** A spawn must never be refused for lack of room (the agent was asked for). Sizes and ids come from tmux's own listing, never from a request. Pure placement logic is easier to test than tmux calls.

## Decision
- **One floor for every pane: 80 columns × 15 rows** (`MIN_COLS`, `MIN_ROWS` in the new pure module `src/place.js`, no I/O). A split is made only when both halves keep it: `fitsH` needs a pane 161 columns wide and 15 rows high, `fitsV` 31 rows and 80 columns (both measured against tmux, spike S-P1d). The floor is the owner's decision of 2026-11-18 (P1 Q1, as recommended).
- **Order, first match wins** (`place()`; its answer is `{ op: 'split', target, dir, tile, placement }` or `{ op: 'window' }`):
  1. **An explicit `under` pane** (spawn sheet or API): split `-v` below it when its window is splittable and the pane passes `fitsV`, or join the tile when its window is an agents window with room. With no room the setting places the agent and the answer carries `moved: 'under'` (the owner's decision of 2026-11-18, P1 Q3, as recommended). The caller may name a pane of any tree.
  2. **`under-last`** with a valid `.last-pane`: the same tests, only when that pane is in the spawn's tree (below), and a tile only when that window is open to the spawn.
  3. **The home window.** The parent pane's window when the parent is in the listing, else the session's current window. It must be splittable. In it: tile it when it is an agents window that is open to the spawn and has room; else split the widest live agent or sub-orchestrator pane of this project that passes `fitsH` (ties go to the higher pane number, the newer pane); else the parent pane when it passes `fitsH` (this shrinks the orchestrator once, to at least 80 columns); else, only with no parent ("you"), the active pane of that window when it passes `fitsH`.
  4. **An existing agents window** of the session that is open to the spawn and has room: the one with the fewest panes, then the lowest window index. Split its biggest live pane, then tile.
  5. **A new window:** `new-window -d -t =<session>: -n agents`. `-d` keeps the user's current window. A session that does not exist is still created with `new-session -d -s <session> -n agents`, and the answer says `placement: 'session'`.
- **Window classes** (from one listing). *ok:* the rows parsed for a window equal its `#{window_panes}` and agree with each other. *Splittable:* ok, not zoomed, `@nika-fit` empty. *Agents window:* splittable and every pane has `@nika-role` `agent` or `sub-orchestrator` and an `@nika-agent` tag of this project (strict parse, as `liveAgents`). A dead pane (`remain-on-exit`) is never split.
- **Never a split target:** a zoomed window or one with `@nika-fit` set. A split there would be hidden by the zoom, and Fit would unzoom, refit and redraw the orchestrator. So `releaseFitted`, `fit.releaseWindow` and the `display-message -p … '#{window_id}'` read are removed, and a spawn no longer touches Fit (the owner's decision of 2026-11-18, P1 Q2, option A as recommended, which replaces ADR 0017's Q3).
- **Re-tiling only an agents window.** After a split into one, nika lists the window again, and runs `select-layout -t @W tiled` only when that listing is trusted as a whole and the window is still an agents window that holds the new pane (not zoomed, no `@nika-fit`). One more listing afterwards is only logged (`nika: spawn placement: a pane of the agents window is below 80x15`). The orchestrator's window is never an agents window (its role is `orchestrator`), so it never gets `select-layout`; nika never swaps, moves, resizes or kills a pane. A sub-orchestrator in an agents window may be re-tiled, never below the floor (the owner's decision of 2026-11-18, P1 Q4, as recommended; rule 3 carries it).
- **Keep trees apart** (owner decisions 2026-11-20, "Keep trees apart" and "Yes, whole trees"). A window is *open to a spawn* only when both hold: (i) a window that holds a sub-orchestrator pane is open only to spawns whose parent is that pane; (ii) every pane in the window is the spawn's parent or has an `@nika-parent` tag equal to the parent's pane id (for "you", every pane has none). The tags come from the `list-panes -a` read the spawn already makes, so there is no new tmux call. A pane the read does not list, a malformed or near-miss tag, a line with more fields than the format, and a pane id seen twice are in nobody's tree: unknown means closed. The two rules are "only when" conditions because a sub-orchestrator is a child of the main orchestrator, so (ii) alone would open a window of sub A to the main orchestrator again.
- **The listing is one piece of evidence.** `list-panes -s -t =<session> -F PLACE_FORMAT` always runs with `-u` (without it, and without a UTF-8 locale, tmux prints a tab as `_`). `PLACE_FORMAT` has 15 tab-separated fields, with the tags a user can write last. The design had 14; `#{pane_active}` was added because "the active pane of the home window" cannot be answered without it. tmux prints a tag raw, so one crafted value can carry a whole forged row. A line that does not parse (check a), or a pane id on two rows (check b), makes the whole listing untrusted: no rows, a new agents window, and one stderr line that says so.
- **Check (c).** A split goes only to a pane that is also in the collector's own `-a` read with the spawn's session, and only when that read is trusted as a whole (every non-empty line has all 11 fields, no pane id twice). Otherwise a new window opens. This stops a forged row that names a pane of another session.
- **Ids.** `@W` matches `WINDOW_ID`. `PANE_ID` is now canonical, `^%(?:0|[1-9]\d{0,5})$`: tmux reads a `%` target by number, so a leading zero would be a second spelling of another pane. The window name `agents` is the constant `AGENTS_WINDOW` (no `#`, which `new-window -n` would format-expand; the existing constant-name test covers it).
- **Failure.** A failed first listing is 502 `tmux_failed` and leaves no brief file, because the listing is taken before anything is written. A failed second listing, tile or read-back logs the step and tmux's exit code only (never listing text, a tag, a name or a path); the spawn still answers 200 because the agent already runs. An `under` pane in a tmux session nika cannot target (a name that does not match `TMUX_SESSION`) is refused with 400 `invalid` before the session listing is read or any file is written.
- **What users see.** The spawn answer carries `placement` (`beside`, `under`, `tiled`, `window` or `session`) and, after a fallback, `moved: 'under'`. `nika spawn` prints `placement:` (and a `note:` for `moved`); `nika status` shows the pane as `<window index>:<pane>`; the app's toast and row menu say which window (`(window n)`). The two placement cards in Settings keep their names and now say "while both panes keep at least 80 columns" and "while both keep at least 15 rows", each "otherwise in a tmux window named agents".
- **Rule text.** Rule 3 gains a "Placement (0.5.4, ADR 0021)" sentence and rule 4 a "Placement (0.5.4)" clause; rule 3's Fit clause lost the `display-message` read. The tree rule narrows what rule 3 allows and is written here and in the spec, not in rule 3.

**What this gives.** In a 200 × 50 window the first agent goes beside the orchestrator (100 | 99). The second finds no pane that passes `fitsH` (99 < 161) and goes to an `agents` window. An agents window takes six agents (grids 2×1, 2×2, 3×2, cells at least 99 × 16), and the seventh opens another one. In a 120 × 40 window, or any window of 160 columns or fewer, no agent is placed beside the orchestrator, and an agents window takes two. The live check confirmed all of these (P1-1 to P1-9; P1-10, on tmux 3.2, was not run).

## Alternatives
- **Keep giving the fitted window back before a split** (P1 Q2, option B; the owner chose option A on 2026-11-18): the CLI would have to read the lease file for the window's own size (a rule 4 change), a spike would have to measure hidden panes of a zoomed window, and `releaseFitted` would stay. It still protects only the app.
- **Refuse a spawn that has no room:** an orchestrator that asked for an agent would have to retry by hand. A new `agents` window always has room.
- **A window per agent:** no shared view, and tmux's window list fills up. The project cap, `min(3N, 24)`, would also be the only bound on windows.
- **Re-tile the home window, orchestrator included:** moves the pane the owner works in. Rejected: the main orchestrator pane is never moved.
- **For an explicit `under` with no room:** refuse with 409 `room`, or split anyway (breaks the floor). The agent is placed by the setting and the page says so.
- **A lower floor such as 60 × 12:** a 121-column window would take one agent beside the orchestrator, at the price of narrower panes. One floor is one rule to explain.
- **A sub-orchestrator's window never re-tiled** (P1 Q4, alternative): more windows. The owner allowed re-tiling on 2026-11-18, and the tree rule now keeps other trees out.

## Consequences
1. In a window of 160 columns or fewer, `beside` never places an agent beside the orchestrator: every agent goes to an `agents` window. The live check ruled this intended. A sub-orchestrator's first agent is `tiled` in its own window, not `beside`: a window that holds only agents and sub-orchestrators of this project counts as an agents window.
2. A user's own pane in an `agents` window makes it no longer an agents window: it is not re-tiled and not a target, and the next agent opens a new one (live check P1-8).
3. The tiled prediction models tmux's algorithm (spike S-P1a: exact for 1 to 10 panes at 200 × 50 and 1 to 6 at 120 × 40, on tmux 3.8). A `tiled-layout-max-columns` the user set, or another tmux, can leave a pane below 80 × 15; the read-back only logs it. It was not run on tmux 3.2, nika's floor: CI's `linux-verify` prints `tmux -V`, and the format fields are long-standing.
4. In an agents window the split comes before the tile. If the tile is skipped or fails, the split's halves stay (for example 49 | 49 columns in a 200-column window) until the user re-tiles, and the next spawn sees the window as too full.
5. Residual risks live in T65 (`docs/security.md`): a forged tag steers where an agent goes, and against one or two crafted values checks (a), (b) and (c) refuse a split of a foreign pane, but a race between the reads (the T36 class), a pane created and not yet fully tagged (milliseconds; it counts as "you"'s tree for that moment), and anything nobody constructed remain.
6. A window that holds a dead pane of another tree stays closed to everyone else until that pane is closed; spawns then open a new window. A false "untrusted" listing (a hand-set tag with a newline) costs the user `beside` for that spawn, and the stderr line says why.
7. A new window in a detached session may be smaller than the floor; the agent starts in it anyway (T65). The CLI and the app tier can race for one agents window (T36), so one pane can end below the floor.
8. `docs/security.md` (T65), `docs/contracts/api-app.md` (the spawn route, the `placement` and `moved` fields, `windowIndex` in the dashboard snapshot) and `docs/design/spec.md` (§9.23) carry the details.
