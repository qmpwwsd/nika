# nika security

What nika defends against, how, and which test proves it. The binding rules are in
[`rules/project-rules.md`](../rules/project-rules.md) (section "Security constraints"). The wire details are in
[`docs/contracts/api-app.md`](contracts/api-app.md). The reasons are in [`docs/adr/`](adr/).

## Trust model

- nika is for **one user on one machine**. It does not defend against another process of the same user that is already
  hostile, with one exception: it tries hard to keep a prompt-injected **agent** (a `claude` process in tmux) from
  driving nika.
- Everything an agent can write is untrusted: transcripts, report files, the session registry, tmux pane titles and
  pane content, project files. nika reads these through `src/fsafe.js`, validates ids with `src/ids.js` and cleans text
  with `src/text.js`. The page renders them with `textContent`.
- Two tiers, two trust levels:
  - **Browser tier**, `nika serve` on `127.0.0.1:3335`. Read-only. Its only side effect is tmux focus. Any local
    process can read it.
    Since 0.4 it also shows, for each session, how many tokens the context holds and the size of the model's window
    (numbers from the `usage` of the last assistant entry in the transcript tail, and nika's own compaction setting;
    no transcript text; constraint 4).
  - **App tier**, `nika serve --app`, a child of the desktop app on a random port. Reachable only with a per-launch
    secret. The privileged routes (`/api/app/*`) are never mounted on :3335.
- nika has no telemetry. The only outbound connection it ever causes is the `claude.ai` link you click, opened by your
  system browser.

## Threat model

"Tests" lists the files under `test/` that cover the threat. "Shell" means `cargo test` in `app/src-tauri`.

| T1 | The app secret leaks | 32 random bytes (base64url) travel only over the child's stdin in the `hello` line. They never reach argv, env, disk, logs, stdout or HTML markup. The server never echoes a bad `hello`. The shell hands the secret to the page through an `initialization_script` that runs only when `location.origin` is the server's; `public/api.js` copies it to a module constant and deletes the global; no other script mentions it. ## Residual risks

Accepted, with the reason.

- **a. Single-user machine.** Any local process, or another account on the same machine, can read :3335: last prompts,
  directories, branches, session ids and report text. Accepted because the tier is read-only, holds no secret and no
  full transcript, and the README says so. Do not run nika on a shared machine. The same holds for what a spawned agent is started with: the brief, the guard prompt and the deny settings are `claude`'s argv (`--append-system-prompt`, `--settings`, `--disallowedTools` and the brief after `--`), so any local process, or another account on a shared machine, can read them with `ps`. The brief never passes through tmux argv, but it is claude's.
- **b. Pane eligibility is a safety net.** A registry pane qualifies only while its current command looks like
  claude, but the registry (`sessions/<pid>.json`) is agent-writable. A same-user agent that can forge it can already
  run `tmux send-keys` itself. The `Bash(tmux:*)` denial of spawned agents does not change that: it is advisory, not a
  boundary (Claude Code matches the literal command text, so a full path, `sh -c` or a script passes). Accepted because
  the boundary is the single-user trust model plus the app secret, and the check still stops honest mistakes, such as
  typing into a shell pane or into a pane id that tmux reused (contract section 5). A pane nika started is held to the
  same test: it qualifies only while its current command looks like claude.
- **c. Spawned agents share a reports dir.** Each gets `--add-dir <reports dir>` (`src/spawn.js:266`). An agent can
  therefore read and write the report and brief files of sibling agents of the same project. Accepted because they
  work in the same repository anyway. `_run-agent` re-validates what it reads (`.agent.json`, bypass refused), and
  the dashboard cleans every string. The `<name>.pane` files in that folder are display only: the agent limit and the
  duplicate-name check count tmux's own tags (T12).
- **d. The secret lives in webview memory.** It stays in the page's module constant for the page's lifetime. A script
  injection in the page could read it. Accepted because the strict CSP, `textContent` rendering and the sink tests
  make injection unlikely, and the secret is useless after the app quits.
- **e. The app is ad-hoc signed, not notarized.** There is no paid Apple identity. A local build runs on the machine
  that built it; a copy moved to another Mac is quarantined by Gatekeeper. Accepted until a signing identity exists;
  see [`packaging.md`](packaging.md).
- **f. AppIndicator on Linux.** The tray needs AppIndicator support. Some desktops (stock GNOME) show no tray icon
  without an extension. Accepted because the window still works: closing it only hides it, and starting the app again
  focuses the existing window.
- **g. Tauri's internal IPC bridge is present in every page.** Tauri injects `__TAURI_INTERNALS__` into the webview,
  including the server's page. No capability file exists, so every command is denied (checked live: plugin, app and
  webview commands all return "not allowed"). Accepted because adding a capability for the server origin is forbidden
  by `rules/project-rules.md` §13.
- **h. `cargo audit` warnings on Linux crates.** Tauri's Linux stack pulls in GTK and zbus crates that RustSec marks
  unmaintained (`proc-macro-error`, `zbus_names`, `zvariant`, `zvariant_derive`) or unsound (`glib` 0.18). They are
  transitive, have no vulnerability advisory, and are not reachable from page content. Accepted until Tauri moves
  off them; CI fails only on vulnerabilities.

- **i. No Claude Code sandbox in 0.2.** Spawned agents run with the permissions Claude Code gives them in your
  account; nothing confines a prompt-injected agent's shell commands, and the deny lists (T3, T4) are advisory. Planned
  as an optional Settings switch (owner decision 2026-11-08). Until then the protection is the single-user trust
  model, the app secret and the permission mode you choose.
- **j. A dead pane kept by `remain-on-exit` (0.4.0).** With tmux's `remain-on-exit` on, a pane whose claude has exited
  stays listed, keeps nika's tags, and tmux still names its command after its argv (so it "looks like claude"). nika
  skips such a pane (`#{pane_dead}`) when it looks for the orchestrator and when it counts agents for the limits, the
  duplicate-name check and the parent, also when this process started it; the 1 s check after Start, Resume and spawn
  reports it as `claude_exited`. The pane mirror and the key routes still accept it while it is in the registry or was
  started by this process: keys to a dead pane do nothing and the mirror shows its last screen. Accepted for 0.4.0,
  because no process receives the keys; the eligibility check reading `#{pane_dead}` is planned for 0.5. Spawn may also
  start a tmux server (0.4.0): from the app it runs with the app child's own environment (constraint 13), the same as
  Start; from the CLI, with the CLI's environment.
- **k. The window route has no rate limit (0.4.0).** `POST /api/app/window` writes one stdio line per call, at whatever
  speed the caller sends. Only a holder of the app secret can call it, the body is one of six fixed actions, the shell
  clamps zoom to 0.5–3.0, and quit, close and minimize act once. A caller with the secret can already do far more.
- **l. Draft sync (0.5, T51).** Five things stay open, none of them a way to send `Enter` or to answer a prompt:
  1. *The one-key window.* A fresh capture is taken before every key or chunk, but a key follows its capture by one tmux round
     trip (tens of ms), the same window as the answer route. A prompt or dialog that opens exactly there receives that one key or
     chunk as literal text; if the draft is a single digit, that digit can answer a numbered prompt. The suggestion accept has the
     same window with a `Tab` instead of text. Accepted: the write stops at the next capture, and the single-user trust model (a)
     applies.
  2. *Wrap cases that read differently from what was typed.* Rows alone cannot always tell a hard newline from a soft wrap
     (`claude-tui.md` §10.4): a newline where the next word would not have fitted (a hard line of exactly the usable width
     included), a word of exactly that width followed by a space and a word, a double space at a wrap, an empty row after a full
     one. The text then reads differently from what was typed, the read-back fails, and the answer is 409 `draft-mismatch`; the
     page then adopts the screen's text, so the next replace writes it back: one line break or space of the draft has really
     changed. Nothing is typed wrongly. The one wrap that cannot be told from rows at all (N-3: a soft wrap between two long words
     that together are wider than the box looks exactly like a word cut at the box width) is not guessed: nika reads that draft as
     unreadable `layout` and pauses the sync, so it never writes over it. The rule that holds in every case: nika's message box
     shows exactly what nika would send, so a text that lost a space on screen is what Send copies back, never a different text
     behind it.
  3. *The cursor of a busy pane.* The cursor rule (the input is where the cursor is, N-1) was checked live on a busy pane
     (2026-11-14, Claude Code 2.1.325, three turns, 8, 8 and 5 samples): the cursor stayed inside the input box while Claude
     worked, empty box and typed text alike. A busy frame with the cursor outside the box was not seen. If one shows up, the
     result is the safe direction: no box, so an append or a type answers 409 `input-unreadable` and syncing waits until Claude is
     idle.
  4. *Two status-line shapes, parked to W11.* A status line that is the glyph alone plus padding (it parses as an empty box) and
     one that draws a plain `────` row can still make the parser read the wrong rows. The cursor rule, which lives in the parser
     since N-1, is then the only layer that refuses: the cursor sits in Claude's real box, not in the rows that were parsed, so
     the capture has no box and the writer, the accept, End and the commands all refuse. W11 is to make the parser refuse these
     shapes by their own shape.
  5. *Accepting a suggestion (W4).* The accept route presses one `Tab` after a fresh capture that showed exactly the suggestion
     the page shows, so the damage of any race is that one key (item 1). Whether Claude takes a real suggestion with `Tab` through
     nika's route, and what `Enter` submits on an empty box that shows one, were not verified live (the owner checks them;
     `claude-tui.md` §10.11). A suggestion of exactly 200 characters may be cut by `clean()` while Claude takes the whole of it:
     the read-back differs and the route answers 409 `draft-mismatch` although the `Tab` worked; the page adopts the screen.

## Supply chain

- Rust crates are limited to the approved list, versions pinned, `Cargo.lock` committed, `cargo audit` in CI.
- Build tools (`tauri-cli`, `cargo-audit`) are installed with `cargo install --locked` at pinned versions and are never
  compiled into the app.
- CI uses only official `actions/*` actions pinned by full commit SHA, a read-only token, no secrets and no publish
  step. The one exception is the `draft-release` job of `release-linux.yml`, which runs on a tag push: it has
  `contents: write` to create a draft release. It checks out no code, so no repository or dependency code runs with
  that token, and it never publishes (the owner does). `test/release.test.js` asserts these rules.
- Node code has no npm dependencies.

Open a private security advisory on GitHub: `https://github.com/qmpwwsd/nika/security/advisories/new`. Please do not
