# nika security

What nika defends against, how, and which test proves it. The binding rules are in
[`rules/project-rules.md`](../rules/project-rules.md) (section "Security constraints"). The wire details are in
[`docs/contracts/api-app.md`](contracts/api-app.md). The reasons are in [`docs/adr/`](adr/).

## Trust model

- nika is for **one user on one machine**. It does not defend against another process of the same user that is already
  hostile, with one exception: it tries hard to keep a prompt-injected **agent** (a `claude` process in tmux) from
  driving nika.
- Everything an agent can write is untrusted: transcripts, report files, the session registry, tmux pane titles and
  pane content, project files. nika reads these through `src/fsafe.js`, validates ids with `src/ids.js` and cleans text
  with `src/text.js`. The page renders them with `textContent`.
- Two tiers, two trust levels:
  - **Browser tier**, `nika serve` on `127.0.0.1:3335`. Read-only. Its only side effect is tmux focus. Any local
    process can read it.
    Since 0.4 it also shows, for each session, how many tokens the context holds and the size of the model's window
    (numbers from the `usage` of the last assistant entry in the transcript tail, and nika's own compaction setting;
    no transcript text; constraint 4).
  - **App tier**, `nika serve --app`, a child of the desktop app on a random port. Reachable only with a per-launch
    secret. The privileged routes (`/api/app/*`) are never mounted on :3335.
- nika has no telemetry. The only outbound connection it ever causes is the `claude.ai` link you click, opened by your
  system browser.

## Threat model

"Tests" lists the files under `test/` that cover the threat. "Shell" means `cargo test` in `app/src-tauri`.

## Residual risks

Accepted, with the reason.

- **a. Single-user machine.** Any local process, or another account on the same machine, can read :3335: last prompts,
  directories, branches, session ids and report text. Accepted because the tier is read-only, holds no secret and no
  full transcript, and the README says so. Do not run nika on a shared machine. The same holds for what a spawned agent is started with: the brief, the guard prompt and the deny settings are `claude`'s argv (`--append-system-prompt`, `--settings`, `--disallowedTools` and the brief after `--`), so any local process, or another account on a shared machine, can read them with `ps`. The brief never passes through tmux argv, but it is claude's.
- **b. Pane eligibility is a safety net.** A registry pane qualifies only while its current command looks like
  claude, but the registry (`sessions/<pid>.json`) is agent-writable. A same-user agent that can forge it can already
  run `tmux send-keys` itself. The `Bash(tmux:*)` denial of spawned agents does not change that: it is advisory, not a
  boundary (Claude Code matches the literal command text, so a full path, `sh -c` or a script passes). Accepted because
  the boundary is the single-user trust model plus the app secret, and the check still stops honest mistakes, such as
  typing into a shell pane or into a pane id that tmux reused (contract section 5). A pane nika started is held to the
  same test: it qualifies only while its current command looks like claude.
- **c. Spawned agents share a reports dir.** Each gets it as its one `permissions.additionalDirectories` entry in the `--settings` JSON
  (`agentSettings`, `src/spawn.js`; 0.5, F18: not `--add-dir`, whose folder Claude Code 2.1.326 asks to trust at every start and whose
  `.claude/commands` it loads, so one agent could plant a command for the others). An agent can
  therefore read and write the report and brief files of sibling agents of the same project. Accepted because they
  work in the same repository anyway. `_run-agent` re-validates what it reads (`.agent.json`, bypass refused), and
  the dashboard cleans every string. The `<name>.pane` files in that folder are display only: the agent limit and the
  duplicate-name check count tmux's own tags (T12).
- **d. The secret lives in webview memory.** It stays in the page's module constant for the page's lifetime. A script
  injection in the page could read it. Accepted because the strict CSP, `textContent` rendering and the sink tests
  make injection unlikely, and the secret is useless after the app quits.
- **e. The app is ad-hoc signed, not notarized.** There is no paid Apple identity. A local build runs on the machine
  that built it; a copy moved to another Mac is quarantined by Gatekeeper. Accepted until a signing identity exists;
  see [`packaging.md`](packaging.md).
- **f. AppIndicator on Linux.** The tray needs AppIndicator support. Some desktops (stock GNOME) show no tray icon
  without an extension. Accepted because the window still works: closing it only hides it, and starting the app again
  focuses the existing window.
- **g. Tauri's internal IPC bridge is present in every page.** Tauri injects `__TAURI_INTERNALS__` into the webview,
  including the server's page. No capability file exists, so every command is denied (checked live: plugin, app and
  webview commands all return "not allowed"). Accepted because adding a capability for the server origin is forbidden
  by `rules/project-rules.md` §13.
- **h. `cargo audit` warnings on Linux crates.** Tauri's Linux stack pulls in GTK and zbus crates that RustSec marks
  unmaintained (`proc-macro-error`, `zbus_names`, `zvariant`, `zvariant_derive`) or unsound (`glib` 0.18). They are
  transitive, have no vulnerability advisory, and are not reachable from page content. Accepted until Tauri moves
  off them; CI fails only on vulnerabilities.

- **i. No Claude Code sandbox in 0.2.** Spawned agents run with the permissions Claude Code gives them in your
  account; nothing confines a prompt-injected agent's shell commands, and the deny lists (T3, T4) are advisory. Planned
  as an optional Settings switch (owner decision 2026-11-08). Until then the protection is the single-user trust
  model, the app secret and the permission mode you choose.
- **j. A dead pane kept by `remain-on-exit` (0.4.0; closed in 0.5.0).** With tmux's `remain-on-exit` on, a pane whose
  claude has exited stays listed, keeps nika's tags, and tmux still names its command after its argv (so it "looks like
  claude"). nika skips such a pane (`#{pane_dead}`) when it looks for the orchestrator and when it counts agents for the
  limits, the duplicate-name check and the parent, also when this process started it; the 1 s check after Start, Resume
  and spawn reports it as `claude_exited`. **0.5.0 closes the rest:** the app tier's pane listing reads `#{pane_dead}`,
  and the eligibility check refuses a dead pane (404 `not_found`, nothing captured or sent) on every route that uses it,
  also one that is in the registry or was started by this process; `GET /api/app/modes` leaves it out. A row whose
  `pane_dead` is neither `0` nor `1` is dropped from the listing instead of being read as running, and Start's
  orchestrator listing uses the same rule. End on such a pane answers `ended: true` (the pane's command reads as gone when `pane_dead` is `1`; 0.5.0 fix), and spawn
  counts a pane whose `pane_dead` is neither `0` nor `1` toward the limits and the name check but never accepts it as a parent (409 `depth`; T36).
  What stays: the listing is cached for 1 s, so a pane that dies inside that
  second can still be sent keys that nothing receives, and the dashboard's focus action (browser tier) still selects a
  dead pane, which is harmless. Spawn may also start a tmux server (0.4.0): from the app it runs with the app child's
  own environment (constraint 13), the same as Start; from the CLI, with the CLI's environment.
- **k. The window route has no rate limit (0.4.0).** `POST /api/app/window` writes one stdio line per call, at whatever
  speed the caller sends. Only a holder of the app secret can call it, the body is one of six fixed actions, the shell
  clamps zoom to 0.5–3.0, and quit, close and minimize act once. A caller with the secret can already do far more.
- **l. Draft sync (0.5, T51).** Five things stay open, none of them a way to send `Enter` or to answer a prompt:
  1. *The one-key window.* A fresh capture is taken before every key or chunk, but a key follows its capture by one tmux round
     trip (tens of ms), the same window as the answer route. A prompt or dialog that opens exactly there receives that one key or
     chunk as literal text; if the draft is a single digit, that digit can answer a numbered prompt. The suggestion accept has the
     same window with a `Tab` instead of text. Accepted: the write stops at the next capture, and the single-user trust model (a)
     applies.
  2. *Wrap cases that read differently from what was typed.* Rows alone cannot always tell a hard newline from a soft wrap
     (`claude-tui.md` §10.4): a newline where the next word would not have fitted (a hard line of exactly the usable width
     included), a word of exactly that width followed by a space and a word, a double space at a wrap, an empty row after a full
     one. The text then reads differently from what was typed, the read-back fails, and the answer is 409 `draft-mismatch`; the
     page then adopts the screen's text, so the next replace writes it back: one line break or space of the draft has really
     changed. Nothing is typed wrongly. The one wrap that cannot be told from rows at all (N-3: a soft wrap between two long words
     that together are wider than the box looks exactly like a word cut at the box width) is not guessed: nika reads that draft as
     unreadable `layout` and pauses the sync, so it never writes over it. The rule that holds in every case: nika's message box
     shows exactly what nika would send, so a text that lost a space on screen is what Send copies back, never a different text
     behind it.
  3. *The cursor of a busy pane.* The cursor rule (the input is where the cursor is, N-1) was checked live on a busy pane
     (2026-11-14, Claude Code 2.1.325, three turns, 8, 8 and 5 samples): the cursor stayed inside the input box while Claude
     worked, empty box and typed text alike. A busy frame with the cursor outside the box was not seen. If one shows up, the
     result is the safe direction: no box, so an append or a type answers 409 `input-unreadable` and syncing waits until Claude is
     idle.
  4. *Two status-line shapes, parked to W11.* A status line that is the glyph alone plus padding (it parses as an empty box) and
     one that draws a plain `────` row can still make the parser read the wrong rows. The cursor rule, which lives in the parser
     since N-1, is then the only layer that refuses: the cursor sits in Claude's real box, not in the rows that were parsed, so
     the capture has no box and the writer, the accept, End and the commands all refuse. W11 is to make the parser refuse these
     shapes by their own shape.
  5. *Accepting a suggestion (W4).* The accept route presses one `Tab` after a fresh capture that showed exactly the suggestion
     the page shows, so the damage of any race is that one key (item 1). Whether Claude takes a real suggestion with `Tab` through
     nika's route, and what `Enter` submits on an empty box that shows one, were not verified live (the owner checks them;
     `claude-tui.md` §10.11); since W13 the submit route refuses such a box (409 `suggestion-shown`, T54). A suggestion of exactly 200 characters may be cut by `clean()` while Claude takes the whole of it:
     the read-back differs and the route answers 409 `draft-mismatch` although the `Tab` worked; the page adopts the screen.
- **m. Fit (0.5, T52).** The fit changes the user's tmux window while the session window is open, and restores it afterwards.
  Twenty-six things stay open, none of them a way to type into a pane (the count said nineteen after F9 added items 20 to 24; item 25 is F10; item 26 is F15):
  1. *A crash leaves the window at nika's size.* `kill -9` of the app tier, a power cut or a hung tmux at quit (the bound is
     3 s; `finish()` holds a no-op SIGTERM listener until the release has ended or hit that bound, so the shell's SIGTERM 2 s after stdin closes no
     longer cuts it short, and the shell's SIGKILL at about 4 s is the only cut left; fix before 0.5.0) skips the restore. The lease file stays, the tag stays, and the window stays zoomed and at nika's size until the next
     app-tier start, which gives it back before `ready` (or drops the lease when the tmux server restarted meanwhile). A quit
     with an acquire in flight can leave a lease the same way.
  2. *The watch is one second late at most.* A user change (unzoom, navigate, split, kill, resize) is seen within one 1 s tick;
     the restore follows within tens of milliseconds (measured on tmux 3.8: the whole restore was done 1009 to 1045 ms after the change). In that
     second the user's terminal shows the window at nika's size, with the fill character around it. Since F4 that only holds for a window nika sized
     before the terminal came to it (item 14), or that nika sized because the session window has focus (F9, item 20: the dots are the ruling's cost).
  3. *Every resize reaches every pane.* `resize-window` sends SIGWINCH to all panes of the window, hidden ones too (two per
     acquire and release; F4: none while a terminal shows the window, except the restore that gives a window back when a terminal comes to it,
     item 14; F9: one per give or take, and a page with focus resizes a window a terminal shows, item 20). With `focus-events on`, zoom and restore flip the active pane, and a pane that enabled focus
     reporting receives `ESC[I` / `ESC[O` (a write to its terminal, not text). Hooks the user set on `window-layout-changed`,
     `window-resized` or `pane-focus-in` run on every step.
  4. *A hook that rewrites the layout or size fights nika.* The read-back after each change sees it, nika releases once, and the
     window stays off (`blocked / changed`) until the session window is opened again or the user presses Fit again in the chip's panel. It never loops.
  5. *`pane-border-status` or anything that makes a pane smaller than its window.* tmux takes one row for a `top` or `bottom`
     border line on every pane, a zoomed or only pane included, so the read-back accepts the window's height or one row less (the
     width and the window size stay exact). A pane smaller by more than that ends `blocked / changed` and the page scales its text.
     A hook that shrinks the pane by exactly one row also reads as fitted (harmless: one row).
  6. *Spawn and the heartbeat.* Since 0.5.4 (ADR 0021) a spawn never splits into a window the fit holds: its one `list-panes -s`
     read shows each window's `@nika-fit` and a window with the tag is not a split target (T65). Between that read and the
     `split-window` (a few tmux calls wide) a beat of another pane of the same window can lease it. The split then lands in a
     nika-sized window; the new pane is an agent pane, so since F2 the watch
     gives the window back and fits it again (about a second, or two when the new pane was not tagged yet at its first look) instead of
     marking a user change. A split between the acquire's resize and its read-back (A4 to A5) still ends `blocked / changed` (off until
     the session window is opened again or the user presses Fit again, which recovers it).
  7. *A spawn that splits a fitted window anyway.* Only through the race of item 6, or a forged tag or listing (T36, T65): the
     watch sees the new agent pane, restores what it can (not the saved layout, the count differs) and fits the window again,
     with no mark (F2). Before 0.5.4 a spawn gave the window back first (`releaseWindow`, owner decision Q3, with a path for a
     pane lock that stayed taken for the whole 5 s wait); that call is gone with ADR 0021. `fit.test.js` covers the refit after a
     split; no test drives the race with a real spawn.
  8. *A busy pane.* A running End, draft write or command that holds the pane for more than 5 s makes the fit answer
     `409 busy`; the lease is kept and the page asks again at its next beat.
  9. *The restore overrides one user action.* If the user resizes the window during a lease that nika resized, the resize back to the saved size
     still runs (R3): the saved size is the only size nika can name, and the alternative is a window left at the panel's size. A lease nika
     never resized (`terminal`, or a zoom-only window) sends no resize back (F4, item 17).
     Everything else the user changed is left alone (layout, zoom and focus are put back only while they are still as nika left
     them).
  10. *tmux versions.* The spike (S10) and the release's live checks ran on tmux 3.8. The `linux-verify` CI job runs the fit
     check (`scripts/linux-verify.sh`, group e; since F4 with two more checks that run a control-mode client, item 15, and since F9 with F9a and F9b, item 23, and since F15 with F15a, item 26) on the Linux runner's tmux (ubuntu-latest ships 3.6a; the CI log of 2026-11-15 shows `3.6a-2ubuntu0.2`): a 3-pane and a single-pane
     window fitted and given back exactly, `select-layout -- <layout>` accepted, `show-options -w window-size` empty while
     unset. The floor, 3.2, is not verified, and neither are the other versions of 3.2 to 3.7. An unexpected answer from tmux
     shows as `blocked / changed` or `blocked / size-option`.
  11. *A pane the user closes by hand that nika tagged as an agent counts as nika's* (F2, owner decision 2026-11-15). nika reads a pane
     that left through the role it saw while the pane lived, so the user's own kill of an agent's pane is not told from the agent
     ending: the fit stays on (it is fitted again) instead of turning off.
  12. *A forged `@nika-role agent`.* Any local process can set the option on a pane the user split, or on its window, session or the
     global scope (`#{@nika-role}` falls back to those). nika then fits the window again instead of staying off. This is a re-fit
     only: the same window, the size the page asked for, the same restore; the user's own changes are still undone only by the
     restore that existed before. Within the single-user trust model (constraint 10, residual a).
  13. *A refit gives the window back first.* tmux applies two size changes in a row (the restore, then the fit), so Claude redraws
     twice within one tmux round trip; and the restore cannot apply the saved layout because the pane count changed, so tmux
     reflows the panes proportionally, as for every restore after a pane-count change. After an agent pane exits, the restore also
     moves focus back to the pane that was active before nika's zoom.
  14. *Up to about a second of dots remains when a terminal comes to a window nika resized* (F4). The watch looks once a second, so a terminal
     that switches to such a window, or attaches to it, shows nika's size with the fill character around it until the next tick (or the page's
     request or the read-back, whichever sees it first). Then nika gives the window back (F9: a give in place, the size back and then the option
     back, with the zoom kept, so a window with several panes no longer shows unzoomed for the refit's ~100 ms). A refit that a page request meets first inside the 30 s
     grace keeps `terminal` but starts the 30 s over (longer, never shorter). Only tmux hooks (`client-session-changed` and the like) could
     remove the second; they write the user's tmux configuration and run commands from hooks, against rules 3 and 11, so they are not built.
  15. *Unverified tmux facts (F4).* `#{window_active_clients}` is in the tmux 3.1 source; spike S16 read that source and ran tmux 3.8, so tmux 3.2
     to 3.5 and 3.7 are unchecked. How iTerm2's tmux integration (control mode) draws a window with a manual size is unverified, and so is tmux's
     `select-layout` of a layout saved at another size (R5 at the final restore after a give or a take, F9, when the terminal's size differs from the window's
     earlier one). The read-back race (a terminal comes between nika's resize and the read-back) is a give in place since F9, so there is no restore
     and no layout to apply there; a window with several panes can still come back from the final restore with slightly different pane proportions
     if tmux scaled them meanwhile (from reading the code; no test measures pane proportions). The two live checks of the `linux-verify` fit group
     (F4a, F4b) run a control-mode client on the runner's tmux, and so do F9a and F9b, which pass on CI (item 23).
  16. *A terminal that arrives or resizes between an acquire's decision and its in-lock read refuses that acquire once* (F4). The window then
     differs from what the decision rested on (`blocked / changed`, no mark, nothing changed); the next beat, within 5 s, lands `terminal`.
  17. *The restore no longer overrides a user's resize of a window nika did not resize* (F4). R3 runs only for a lease nika resized (`sized`), so
     a user who resizes a zoom-only window by hand during the lease keeps their size at the restore. That is the intended change; it also means
     item 9 holds only for leases nika resized.
  18. *Small text* (F4). A big terminal and a small panel scale the text down (about 0.42× for a 200 × 50 pane in a 112 × 21 panel); below 0.4×
     the text stops shrinking and the panel scrolls (W7 Q2).
  19. *The zoom shows in the user's terminal and moves its focus to the mirrored pane* (F4, kept by the ruling and already a consequence in ADR
     0017). While a terminal shows a window with several panes, nika zooms the pane there too, until the session window closes.
  20. *A terminal shows dots while the session window has focus, and every pane of the window redraws once or twice per switch* (F9, the ruling's
     accepted cost). With focus nika sizes the window to the panel even when a terminal shows it, so the terminal shows the fill character around
     the smaller window, or a cropped view when it is smaller than the panel. tmux resizes the layout of a zoomed window as a whole, so each give
     or take reaches every pane (the hidden agent panes too) and each Claude redraws; its copies land in the pane's tmux history, not in the outer
     terminal's scrollback, and there are none in Claude's own full-screen mode (not verified here: no claude run).
  21. *`focus` is the second request value that decides a resize* (F9). A forged `true` (a local process with the app secret, rule 10, or a
     compromised page) gives W7's behaviour: the window is sized to the panel and a terminal shows dots; a forged `false` gives F4. It is bounded:
     a boolean checked at the route and in `src/fit.js`; never a target, a stored value, a lease-file key or text; recorded only in the lease the
     request's own pane holds; 4 requests a second per pane; at most 12 takes a minute per window (memory only, so a restart of nika forgets the
     count); a give is never limited.
  22. *The webviews' focus events differ and changed in 2026* (F9; WebKit bug 305846 and 119727). The page treats `focus`, `blur` and
     `visibilitychange` as triggers only, reads `hasFocus()` and the visibility fresh, polls once a second, and reads anything unreadable as no
     focus, so a missed event costs up to about a second and a wrong `hasFocus()` makes nika behave as F4. Only the owner's live check proves
     macOS; nothing proves WebKitGTK until a Linux user runs it; the Linux CI cannot test a webview.
  23. *Unverified facts (F9).* That `resize-window` on a zoomed window resizes every pane and leaves the zoom is from the tmux source and spike S16
     (Q4, tmux 3.8), not from a claude run; the redraw count per switch is unmeasured. The checks F9a and F9b of the `linux-verify` fit group pass
     in the CI job on the runner's tmux (3.6a at the last log, with a control-mode client); they do not run on macOS. The final restore's `select-layout` of a layout saved at another
     size (item 15) is from the source and unverified on 3.8.
  24. *A hidden session window keeps its lease; a native dialog blurs it; a pointer can change focus* (F9). Hiding or minimizing is a blur: the
     size goes back at once and the lease stays, so a terminal showing a window with several panes keeps the pane zoomed until the window is shown
     again, lapses (15 s without a request, if the webview stops its timers) or closes. The attach chooser blurs nika for as long as it is open (two
     resizes per pick). A window manager with focus-follows-mouse could flip the focus fast: the page's 150 ms settle (F10; 400 ms in F9) filters less of a pass of
     the pointer and the cap bounds the rest. In the app tier there is one session window today (the shell denies new windows), so no second page can take the
     size.
  25. *The page may ask for a size larger than its panel, and it holds its own drawing for 1.2 s* (F10, F11, F16). To make room for Claude's input box and footer the page asks once for
     33 rows or more (F11: at any commit it also asks for the rows its mirror hides under the input-box strip, at most 200 in all) with the columns in the panel's proportion, still the same body `{ cols, rows, open, focus }` and still inside the route's ranges (40–400 × 10–200, checked at the route
     and again in `src/fit.js`); the server cannot tell it from a panel of that size, and every rule of this entry applies to it (the squeeze rule, 4 requests a second per pane, the
     lock, the lease). It is a renew from a page that holds the lease, not a take, so `TAKE_MAX` is not touched by it; later focus takes ask the same size and count in the 12 a minute
     as any take, so a forged or looping page gains nothing the existing bounds do not already stop. The page's redraw hold and its waiting requests (scroll, Send, the draft write,
     the mode switch, quick-action commands, the End dialog) delay a request by up to 1.2 s (2.4 s with the room step) and send nothing on the strength of the held frame: every
     server gate (T23, T26, T39, T51, T54) takes its own fresh capture as before. The cost is visible, not a safety one: smaller text where the room is on, and the top rows
     of Claude's frame hidden while a prompt panel or a tall draft makes the box shorter (the mirror stays pinned to the bottom).
     F16: while a question dialog is cut off at the top it asks for up to 120 rows, at most four steps and one size-back per question; the
     grow never sends a key, and answering the question keeps every gate of T37 (the dialog route takes its own fresh capture, so the pane stays grown while the question is open). The ask is a renew, not a take, and
     the rate of 4 requests a second per pane bounds a looping page. The cost is visible, not a safety one: while this window has focus and a terminal also shows the window (F9, item 20), the
     terminal shows only part of a window taller than itself until the question closes or the user clicks into the terminal (how tmux pans it is not verified).
  26. *Any pane may be squeezed while the session window has focus, and the way back flashes every pane* (F15, owner decision 2026-11-16, "resize while
     zoomed", asked twice). (a) A shell or an editor in a hidden pane sees a narrow window while the page has focus and may keep lines wrapped at that
     width; nika does not ask the other panes what they run, because the zoom hides them. (b) On blur the give applies the saved layout, which unzooms the
     window, and zooms the mirrored pane again, so a terminal that shows the window briefly shows every pane (the time was not measured; a control-mode
     client sees the `*` and `*Z` flags alternate in its `%layout-change` events). (c) Each take and each give sends SIGWINCH to every pane (item 3's count
     is two more per cycle when a layout is put back), at most 12 takes a minute per window, and the user's tmux hooks on `window-layout-changed`,
     `window-resized` or `pane-focus-in` run on each. (d) tmux cannot shrink a window below its minimum: 2n − 1 columns for n panes side by side (rows
     for stacked panes), 1 on the other axis; below it `resize-window` exits 0 and prints nothing, so the read-back finds the window larger than the panel
     and the fit ends `blocked / changed` (spike S-F15, tmux 3.8; mixed grids not measured). (e) A window nika had *grown* (a panel bigger than the window)
     and that a later renew squeezes has no own-size layout to read, because tmux scaled it: it keeps no `layoutT`, its give is the plain one, and the
     hidden panes get their layout back only at the release (R5 with `layout0`), not at the blur. (f) A layout that cannot be read (a `#` in it, say) at a
     take means no squeeze: the pane stays zoomed with scaled text, and the watch tries again at each tick while the page has focus. (g) A user who
     changes the layout, size or zoom while the window is squeezed is a user change or `changed` (the lease is released once; R5 is skipped when the user
     changed the layout), and a crash while squeezed is recovered from `layout0` at the next start, not from `layoutT`, which is memory only. (h) Facts: the
     give sequence was exact in 870 of 870 cycles on tmux 3.8 with no client, a control-mode client and a tty client (S-F15); `select-layout` of a layout
     saved at another size scales it with `window-size manual` and resizes the window with the option unset, which is why the resize back and the option
     come first; tmux 3.2, the floor, and the other versions are not checked, and `F15a` runs on the runner's tmux only. A different tmux that restores the
     layout differently makes the read-back release with `changed`, not leave a wrong layout. Nothing a request carries reaches the layout: the `select-layout`
     argument is tmux's own output of the same locked listing, stripped and validated (printable ASCII, no `#`, at most 8 KB).

- **n. Scroll (0.5, T39).** Seven things stay open, none of them a way to answer a prompt or to type text:
  1. *A prompt opens inside the window.* A prompt or dialog that opens between the route's fresh capture and its keys (one `keys.send` of ≤ 8
     keys, about 5 to 40 ms) receives them. Claude binds PageUp/PageDown/End-like keys to move the highlight of its select lists, so the
     highlight can move; nothing is answered (no `Enter`, digit, `Space`, `Tab` or `Escape` goes). nika's prompt buttons answer by digit
     after a `sig` check over the rows, which a moved highlight changes, and Send stays gated while a prompt shows; an `Enter` typed in the
     terminal itself picks the moved option. The same single-user race as residual b. (Live check L9: with a prompt on screen the raw keys
     moved the prompt's rows off the screen and back, and the highlight never moved.)
  2. *The user's own `keybindings.json`.* It can rebind PageUp, PageDown, Ctrl+Home or Ctrl+End. nika never reads that file (rule 4), so on
     such a setup the keys do what the user bound, the same as pressing them in the terminal.
  3. *The meanings come from Claude Code 2.1.325.* The key meanings and the pill are from spike S5, its default keybindings and the live
     checks of 0.5 (`claude-tui.md` §12). A changed pill only changes the display; a changed key meaning is caught by the gate only when it
     comes with a changed footer.
  4. *Queued pages are not re-gated at the send.* The page's planner can hold several pages while a request is in flight (one request at a
     time, at least 100 ms apart, at most 8 pages); a queued page is not checked against the screen when it is sent. Only the server's gate
     decides, and it answers 409 with nothing sent.
  5. *An aborted call does not cancel the server.* The page gives up on a request after 10 s. If the keys went out and only the answer was
     lost, the planner may scroll again. Bounded by 10 requests per second and 8 pages.
  6. *The keys of one request go one tmux call each.* A Stop (outside the lock) can land between them: the 40 ms check is made before the
     capture and again right before the first key, not between keys.
  7. *The display can lag or misread.* A stale cached capture can flip `scrolled` for one tick (live check L14: narrow, seen only in
     process). A pill that is wrapped over two rows or counts more than 999 new messages is not matched. Words that read `Jump to bottom`
     or `N new message(s)` printed in exactly the pill's colours set `scrolled`: a forged pill changes the display only, never whether a
     key goes out. The `(click) ↓` variant of the pill was not seen live and is covered by a unit test only. For about 8 s after a paste
     Claude's footer reads `paste again to expand`, so the route answers 409 `screen-unclear` (the safe direction; live check L3).
- **o. Attachments (0.5, T38, T55).** Six things stay open (items 4, 5 and 6 each gained a residual in the final review):
  1. *The window before the `Enter`.* The few milliseconds between the last capture and tmux delivering the `Enter`, as T26, T51 and T54. Since
     W13 it is no longer hidden behind an idle check: a running turn can open a prompt at any moment, and a prompt drawn inside the window
     takes the `Enter`. The send refuses every screen `submit` refuses; it cannot use `submit` itself because it must paste and re-check
     between pastes.
  2. *A process of the same user.* It can swap a stored file between nika's check and Claude's read, or read it (single-user model, rule 10).
     nika reads the content back only in the image route (T61), never in the send.
  3. *The folder grant.* Claude's Read prompt for a PDF or text file offers "allow reading from this folder during this session": that
     covers the repository's whole attachments folder, i.e. the files of the last `keepDays` days, not only the one file. Under the user's
     own allow rules there may be no prompt at all. The transcript keeps images as base64 and the paths (Claude's storage, not nika's).
  4. *A page that leaves.* Since 0.5.4 (AT) leaving the page deletes nothing. Unsent files stay, and the chips come back from the server's
     tray when the session window opens again (T80, T81). A chip removed while it was still uploading, on a page that left before the upload
     answered, comes back on the return, because its late upload lands in the tray; removing it again deletes it. After a partial send the
     files whose paths sit in Claude's input stay, so Claude's Read of them works. A page that never comes back leaves its files until the
     session ends or `keepDays` passes. An app restart forgets the tray (it lives in memory) and leaves the files to `keepDays`.
  5. *What the chooser leaves.* A file the page has no room or no right to keep after a pick (a send began, the tray filled) is deleted best
     effort and otherwise stays stored until it expires. A pick that arrives while an upload runs fails `busy`. The shell drops, without a word,
     a path beyond the sixth. Smaller points: two calls in `public/attach.js` sit outside a `try` (unreachable today), the shell's release
     of the dialog slot is not keyed by request id (safe by construction), and the status line is announced when it goes from hidden
     to shown. A picked file on a hung network mount keeps the chooser slot `working` (no timeout; Add project shares the slot), see T55.
  6. *Disk and memory.* nika keeps a copy of every attached file for up to `keepDays` days (Settings says so). An upload is held in memory
     while it is decoded: on macOS six 7.8 MB uploads took the process from about 25 MB to about 160 MB right after (RSS 70 to 206 MB), 65 MB a
     minute later and 36 MB after five (RSS 100 MB); one save at a time and 12 MiB per body bound what is kept. The one-at-a-time check runs
     after the route has read and parsed the whole body (`save()` answers 429 `busy` only then), so several bodies of up to 12 MiB can be held in
     memory at once; that needs the app secret, and admission is limited to 30 a minute after the body is read. Not fixed: the check would have to move
     before the body is read, in `src/api-app.js`.

- **p. Question dialogs (0.5, T37).** Six things stay open:
  1. *The window before a key.* tmux has no compare-and-send. If the user closes the dialog, or Claude opens another, in the few
     milliseconds between the last check and a key, a digit becomes draft text, or an `Enter` submits Claude's input box. A Decline's `Escape`
     has the same window: if the dialog was answered in the terminal in those milliseconds, the turn is running again and the `Escape`
     interrupts it. The same class as T26, T51 and T54.
  2. *An identical dialog asked again.* Without a call id, a dialog Claude asks again between the page's last capture and the request,
     identical in every parsed part (same tab, headers, question, labels, descriptions), is answered as the first one would have been. The
     answer means the same thing there; a model turn takes seconds and the page polls at 4 Hz.
  3. *`Escape` from the message box.* The box's `Escape` is a passthrough, as in the terminal and as for a permission prompt: while a dialog
     shows it declines the dialog without the form's `sig` check (ruling 2026-11-15). The same single-user race as residual b: the user pressed
     the key on purpose, and `Escape` is the one key the passthrough has always sent.
  4. *The form stays locked.* After 409 `dialog-touched` or `dialog-focus` every control, Decline included, stays off until a new `sig`,
     `dialog: null`, a reload or, since 0.5.2 (R4, owner decision 2026-11-17), the user presses **Try again** (ruling 2026-11-15: the problem line sends
     the user to the terminal to finish it). Try again sends nothing and only turns the controls on; the mitigation is unchanged, because no key goes out
     without the route's fresh check of the screen, the focus and the text, which refuses a dialog that is still off. Not a security gap, but the
     user cannot decline from nika until then.
  5. *A longer wait than the lock.* A dialog request holds the pane lock for up to 24 rounds, each a fresh capture and a settle of at most 4 x 150 ms;
     a fit, scroll, attachment send or draft write waits at most 5 s and then answers 409. `STEPS_MAX` (24) is a backstop that no consistent
     screen reaches, because the check against the screen the last key was proven on stops a screen that undoes a key.
  6. *Claude's task list under a dialog or a prompt (F13).* The cut is fitted to Claude 2.1.325's drawing: a block with no blank row, or two or more,
     between the rule and the header (not seen in the spike), a notification row, or a second row under a task is not cut, and the banner stays. A
     task label that mentions bypass makes the guard refuse (409 `bypass-prompt`; terminal only), which is the intended fail-closed side. The `│ ` bar shape of a question row that is only the bar, with no text, is unverified and reads as `layout`.
- **q. Feedback survey (0.5, T58).** Seven things stay open, none of them a way to answer a prompt or to type more than one digit:
  1. *The window before the digit.* tmux has no compare-and-send. The last screen check is the second capture (S1), taken after the fresh registry state read, so the window is
     the time between that capture and tmux delivering the digit (one capture round trip plus the send), not the whole snapshot of the state read. If the survey closes, or the
     user types in Claude's box, in that window, the digit becomes draft text. The answer is 409 `not-taken` with `sent: 1`, and the page says the number may sit in Claude's input
     box. The same class as residual p, item 1, and T26. The second capture costs one extra tmux capture per click.
  2. *Vim NORMAL that nika never saw as vim.* nika knows a pane is in vim only after it has seen `-- INSERT --` on it in this process. On a pane whose INSERT it never saw, vim
     NORMAL reads as plain mode, so the digit can land as a vim count (the survey stays and the digit does nothing). The answer is `not-taken` with `sent: 1` and the digit stays
     in place; no other key is sent.
  3. *Rows a model printed.* Rows that look exactly like the survey, printed by the model directly above the input box with one free row before its top rule, can make the
     page offer buttons. The most a press can do is type one digit into an empty box, which reads back as `not-taken`. nika does not check the rows' colour (themes vary).
  4. *A slower Claude.* The read-back stops after 1 s. A Claude that takes the digit later gives `not-taken` although the answer lands; the page locks the buttons until the `sig`
     changes, and the `sig` is held for 3 s on the server.
  5. *The hold lives in memory.* The 4 s ban on `Escape` is per controller instance: an app-server restart forgets it, and the user's own `Escape` through the keys route or the
     message box still undoes a rating (it is Claude's own "Esc to undo", and the user pressed it on purpose). Stop and End answer 409 `survey-undo` for up to 4 s after a
     rating, which can be a surprise right after a click.
  6. *The transcript question is the terminal's.* It is not built: its layout is unrecorded and its keys are letters (`y`, `n`, `d`). A later round needs a live capture and a new
     body shape; until then the user answers it in Claude. No other survey (the long-context and memory variants) is offered either: their rows were never captured.
  7. *The row after a rating is matched by its start, from one spike.* `(Optional) Press [1] to tell us more` was seen in 10 of 10 captures of one rating, at 120 columns, at
     column 0, never wrapped, so only the start of the row is matched, and only at column 0. The `Thanks for the feedback!` row above it is not matched (it always came with the other, and a model's own
     line saying so would hold the sync until it scrolls off). A row at column 0 that starts exactly `(Optional) Press [1] to tell us more` (not a reply row: Claude indents those) pauses the draft sync and Send's
     typing while it shows (fails closed). A dialog that opens in those seconds reads `unreadable / survey` and is answered in the terminal. Whether Claude takes a `1` there from the
     box after a pause (as the survey does) or as a keypress was not tried; nika types nothing there either way.
- **r. Typed `/compact` (0.5.4, T72 to T74).** Seven things stay open:
  (1) A key the user types into the real terminal, or a turn that starts, between nika's last capture and its `Enter` goes out with or ahead
     of `/compact`: Claude may answer an unknown command, or run `/compact` after that turn.
  (2) A forged transcript size gets a session compacted once per crossing, at most every 10 min, under the single-user model (constraint
     10), like T36.
  (3) A finished session waiting to be closed compacts once (owner, 2026-11-19).
  (4) An app restart arms every pane again, so a session that stays past the point (its summary is still too big, or Claude's compaction
     failed) gets one more attempt 60 s after each restart.
  (5) Claude's own compaction can run at the same moment (its pre-request check, or its idle compaction); the typed `/compact` then waits in
     Claude's queue or meets a busy screen and is not typed.
  (6) Not reached (owner, 2026-11-19): a plain terminal, another tmux server, the browser tier alone, a session that keeps working past the
     point.
  (7) Keys that reach the pane through the keys route (the page's passthrough, the user's own typing) take no pane lock, and Stop runs
     outside it, so they can interleave with nika's own keys during an attempt; the echo check then refuses `Enter` and nika removes only
     its own text, and a mixed text stays in the box (T73).
- **s. Question dialogs with a preview (0.5.4, T75 to T79).** Eight things stay open:
  (1) nika never sends `Escape` inside the notes input; when the user presses it (in the mirror, the message box or the terminal) Claude
     closes the field and keeps the note (live check LC-QPB), and a user who opens notes in the terminal closes them there.
  (2) Whether a note reaches Claude, and where, was not seen live; nika shows what it typed and Claude's own row, nothing more.
  (3) Claude's fallback line replaces a preview at sizes nika cannot predict; the page then shows the labels only and says so.
  (4) A preview step on a multi-select question or a one-question form was never seen live; both read `unreadable` (the banner).
  (5) The preview text can hold the user's code and paths: shown in the app only, never logged, never on :3335.
  (6) If Claude's focus moves while the user types a note (keys typed in the terminal itself), the form follows it, and `Enter` in the note
     field then answers the option the form shows checked, with the note written for the other one. Nothing is answered that the page does
     not show; the user checks the selected option before pressing `Enter`. Accepted for 0.5.4.
  (7) A note that wraps on a step whose preview is cut can make Claude hide one more preview line; nika then stops before `Enter` (409
     `preview-changed`) and the note stays in Claude's notes field: the user finishes in the terminal.
  (8) A plan question is not readable below about 109 columns, or at 85 columns or fewer (its prompt wraps); the page shows the banner that
     says to answer in the terminal.

## Supply chain

- Rust crates are limited to the approved list, versions pinned, `Cargo.lock` committed, `cargo audit` in CI.
- Build tools (`tauri-cli`, `cargo-audit`) are installed with `cargo install --locked` at pinned versions and are never
  compiled into the app.
- CI uses only official `actions/*` actions pinned by full commit SHA, a read-only token, no secrets and no publish
  step. The one exception is the `draft-release` job of `release-linux.yml`, which runs on a tag push: it has
  `contents: write` to create a draft release. It checks out no code, so no repository or dependency code runs with
  that token, and it never publishes (the owner does). `test/release.test.js` asserts these rules.
- Node code has no npm dependencies.

## Reporting a vulnerability

Open a private security advisory on GitHub: `https://github.com/qmpwwsd/nika/security/advisories/new`. Please do not
file a public issue for a vulnerability. Say which tier is affected, how to reproduce it, and which version you used.
