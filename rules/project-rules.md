# nika project rules

Scope: binding for every session and agent working in this repository. They extend `~/.claude/ORCHESTRATION.md`; on a conflict this file wins.

## What nika is

A local dashboard and control panel for the Claude Code agents on this machine, grouped by git repository, in two tiers:

- **Browser tier (read-only)**: `nika serve` on `127.0.0.1:3335`, installed with Homebrew (`brew install qmpwwsd/tap/nika`) and run as a launchd/systemd service (`brew services start nika`). Lists agents; its only side effect is tmux focus. Unchanged from 0.1.
- **App tier (privileged)**: the desktop app (Tauri v2, macOS and Linux, tray icon) runs its own private server `nika serve --app` on `127.0.0.1:<random port>`, child of the app, secret handed over stdin. Only this tier has history, pane mirror and input, session control (mode, End, commands, models), spawn, start orchestrator, add project, settings and apply rules (`/api/app/*`). These routes are never mounted on :3335.

Contracts: `docs/contracts/api-app.md`. Decisions: `docs/adr/`.

## Stack and commands

- Node >= 22, ES modules, **zero npm runtime and dev dependencies** (stdlib only). A new npm dependency needs the owner's approval.
- Rust (Tauri v2) for the desktop shell only, under `app/src-tauri`. Approved by the owner on 2026-11-08: `tauri` (tray-icon, image-png), `tauri-build`, `tauri-plugin-single-instance`, `tauri-plugin-dialog`, `tauri-plugin-autostart`, `serde`, `serde_json`; on 2026-11-13: `objc2-foundation` (macOS only, to register nika's own press-and-hold default in memory). Versions pinned, `Cargo.lock` committed, `cargo audit` in CI. Any other crate is a new approval. Build tools approved by the owner on 2026-11-08, installed with `cargo install --locked` at pinned versions, never compiled into the app: `tauri-cli` (bundles) and `cargo-audit` (CI). Bundle id `io.github.qmpwwsd.nika`, display name `nika`.
- Tests: `node --test "test/*.test.js"` (`npm test`); `cargo test` under `app/src-tauri`. Every collector, route, store function and write path has a `(+)` case and a `(−)` case. `test/hygiene.test.js` must stay green: no home paths, scratchpad paths, emails, real-looking session ids or UUIDs, API keys or `.local` hosts anywhere in the repo.
- Run locally: `node bin/nika serve`, `node bin/nika status`; app tier: `node bin/nika serve --app` with a piped stdin (`hello` line), or `nika app`.
- Formula lives in the separate repo `qmpwwsd/homebrew-tap` (`Formula/nika.rb`).

## Security constraints (never relax)

1. The server binds `127.0.0.1` only and rejects any `Host` header other than `127.0.0.1:<port>` or `localhost:<port>`.
2. State-changing routes (`POST /api/focus`) require `Content-Type: application/json`, the per-process `X-Nika-Token`, and a matching `Origin` when present. No CORS headers.
3. Subprocesses run with `execFile` and fixed argument arrays, never through a shell. A tmux pane id must match `^%\d+$` and exist in the current `list-panes` output, or be the id tmux itself returned from `-P -F` a moment ago (`tagPane`, `earlyExit`); it is matched against `PANE_ID` either way. tmux shell-commands are passed as multiple arguments (no `sh -c`); session names match `^[A-Za-z0-9_][A-Za-z0-9_-]{0,47}$` and targets are exact (`=<name>`, `%n`); `send-keys` text always follows `-l --`. tmux format-expands `-c` (a start directory is passed through `tmuxLiteral`, every `#` doubled) and also `new-session -s`, `new-window -n` and `select-pane -T`: those three are safe only because `TMUX_SESSION`, `AGENT_NAME` and nika's constant window names and titles contain no `#`, and a test asserts it. tmux `new-session -e` and `new-window -e` (0.4, ADR 0014) take a literal value (no format expansion; spike S2), and nika passes only the two auto-compact names, each with a value `compactLaunch` made of digits and at most one dot. `new-session -e` is session-scoped, so right after it nika runs `set-environment -t =<session> -u <NAME>` for each of the two names (fixed argv, exact target, best effort); `new-window -e` is pane-only. `new-session -e` needs tmux 3.2. Pane tags are set with `set-option -p` and fixed argv arrays (their values are not format-expanded, and none contains `#`): `@nika-role` is `orchestrator`, `sub-orchestrator` or `agent`, `@nika-agent` is `<project key>/<AGENT_NAME>` built from validated parts (an orchestrator's is `<project key>/orchestrator`, set when nika starts, resumes or adopts it), and (0.4, ADR 0013) `@nika-depth` is a constant `1`, `2` or `3` that nika computes from the parent's role and `@nika-parent` is a pane id (`^%\d+$`) taken from tmux's own listing, never request data, argv, env or a file.
4. nika never reads `*.key` files, `daemon/control.key`, `.env*`, `cc-socks`, the `hooks`, `permissions`, `env`, `apiKeyHelper`, `mcpServers` or `model` keys of any Claude settings file, or any credential path. The one exception is a project's `.claude/settings.local.json` at rules-apply time: nika parses the file as JSON to merge `enabledPlugins`, but never interprets, shows or sends any other key (they are copied verbatim, and the apply keeps a byte-for-byte backup of the file in nika's state dir). The browser tier reads only: `sessions/<pid>.json`, `projects/**/<uuid>.jsonl` (head and tail chunks; from the tail, also the `usage` numbers and the model id of the last assistant entry, nothing else of it: the context size, 0.4), `subagents/*.meta.json`, spawn report files (`<name>.session|.md|.rc`, in the scratchpad and in nika's own `reports/` dirs), nika's own `config.json` (project list, per-project config and the compaction setting), the pane tags nika sets itself (`@nika-role`, `@nika-agent`, `@nika-depth`, `@nika-parent`, from `tmux list-panes`, each parsed strictly and dropped when it does not parse; 0.4), `.git` / `commondir` files and, on Linux, `/proc/<pid>/stat` of the registry pids whose `procStart` is digits (the `starttime` field only, ≤ 4 KB). The app tier additionally reads: full transcripts, paginated with bounded windows; `tmux capture-pane` of live Claude panes and nika-started panes only, and only while the pane's current command looks like claude (`CLAUDE_COMMAND`; a stale or reused pane id never qualifies); the installed plugin names and their `installPath` values in `installed_plugins.json` (a path is used only when its realpath is inside `<claude dir>/plugins/cache`; `<claude dir>` is the Claude config dir, `CLAUDE_CONFIG_DIR`, default `~/.claude`); the YAML frontmatter (first 4 KB; keys `name`, `description`, `argument-hint`, `user-invocable`; never the body) of top-level command and skill files in `<claude dir>/{commands,skills}`, `<project>/.claude/{commands,skills}` and installed plugins' `commands/` and `skills/` (0.3); a project's `rules/orchestration.md`, `CLAUDE.md`, `.claude/settings.local.json` and `.gitignore` for preview and apply, and a project's `AGENTS.md` (G7, 2026-11-14): its type first with `lstat` without following (absent, regular file, symlink or other), and its content only when it is a regular file, read through `src/fsafe.js` like `CLAUDE.md` (no follow, user-owned, single link, bounded, UTF-8; a buffer sized by the file) for the preview and the apply. The rules state (the project list's badge on every poll, and `nika projects list`) reads `rules/orchestration.md`, `CLAUDE.md`, `AGENTS.md` (same rules) and `.gitignore` the same way, and never opens a symlink, folder or FIFO. On macOS the CLI and the app tier also read `Contents/Info.plist` (≤ 64 KB, bundle id and version only) of nika's own app bundles: the source and `~/Applications/nika.app` (ADR 0011).
5. A file path never comes from a request. Report files are looked up by session id in the index nika built itself. Projects enter only through the native folder picker or `nika projects add <dir>` on the CLI, are stored as realpath and referenced by key (`^[a-z0-9]{16}$`, sha256 of the realpath) everywhere else.
6. Every transcript-, pane- or report-derived string is rendered with `textContent`; the page ships a strict CSP (no inline script or style). The pane mirror keeps only whitelisted SGR codes server-side; OSC, DCS, other CSI and C0/C1 never reach the page.
7. Test fixtures are synthetic. Never copy a real transcript, session file, account id, prompt, rules file or path into the repository. Rule templates under `templates/` are written from scratch, never copied from a private project or `~/.claude`.
8. No hardcoded user paths: use `os.homedir()`, `CLAUDE_CONFIG_DIR`, `process.getuid()`, `XDG_*` via `src/paths.js`.
9. Every file under `~/.claude`, a scratchpad, a project or nika's own dirs is agent-writable: read it through `src/fsafe.js` (O_NOFOLLOW, O_NONBLOCK, regular file owned by the user, bounded size), validate ids at the boundary (`src/ids.js`), and pass display text through `clean()` / `cleanBlock()` (`src/text.js`).
10. Single-user machine assumption: any local process can read the browser tier. The README says so; do not add data to :3335 that would make this worse (no secrets, no full transcripts). The app tier is reachable only with the per-launch secret: random port, 256-bit secret over stdin, `X-Nika-App` timing-safe, `Origin` / `Sec-Fetch-Site` checked, JSON for writes, `no-store`. The secret never touches argv, env, disk, logs or HTML markup.
11. **Writes.** nika writes only through `src/fwrite.js` (real user-owned dirs, targets absent or regular single-link user-owned files, O_EXCL temp file + fsync + rename, 0600/0700 for nika's own files; an existing in-project file keeps its mode minus group/other write, a new `settings.local.json` is 0600 and other new in-project files 0644; an in-project folder may be group-writable only on Linux when its group is the user's primary group, never world-writable). Its own files live in `${NIKA_CONFIG_DIR || XDG_CONFIG_HOME || ~/.config}/nika` and `${XDG_STATE_HOME || ~/.local/state}/nika`. Into a project it writes exactly `rules/orchestration.md`, `CLAUDE.md` (one `@rules/orchestration.md` line), `AGENTS.md` when it is a regular file (the same one line), `.claude/settings.local.json` (only `enabledPlugins`; all other keys copied verbatim and deep-equal asserted) and, opt-in, one `.gitignore` line; always after a diff preview, explicit confirmation and a hash check, with a byte-for-byte backup in nika's state dir, never inside the repo (the last 10 backup folders per project are kept; after a successful apply the older ones are removed, and only entries named like a stamp nika wrote that are real directories owned by you; a symlink, a file or any other name is never followed or deleted). After each in-project rename the directory chain is re-checked and the target must resolve inside the project root, else the file is unlinked and the write refused with `ESYMLINK` (`verifyInside`; a swap in the remaining window needs write access to the project folder, `docs/security.md` T8). nika never runs `git add`, `commit` or `push`. **`AGENTS.md` and `CLAUDE.md` (G7, owner decision 2026-11-14):** other coding tools read `AGENTS.md`, Claude reads `CLAUDE.md`, so both carry the line, and Claude must load the rules once. `AGENTS.md` is written before `CLAUDE.md`, with the same backup, hash check, `verifyInside` and mode rules; a `CLAUDE.md` with an `@AGENTS.md` (or `@./AGENTS.md`) import line outside a code fence, beside a regular `AGENTS.md`, gets the rules through it and is left as it is (nika never adds the line there and never removes one; if it has its own line from an earlier apply, the preview says Claude may read the rules twice); a project with only a regular `AGENTS.md` gets a new `CLAUDE.md` whose whole content is `@AGENTS.md`. A symlinked, folder, FIFO or other non-regular `AGENTS.md` is never followed or opened: beside a `CLAUDE.md` it is shown as `skipped` with a note and `CLAUDE.md` gets the line itself; alone it refuses the apply (`ESYMLINK` for a symlink, `ENOTREG` otherwise). **App copy (owner decision 2026-11-09, ADR 0011):** on macOS nika also writes exactly `~/Applications/nika.app`, a `ditto` copy of the nika.app that came with this install, only on `nika app install`, the app's Add/Update button, or a launch command refreshing a copy nika made before (state marker) after an upgrade. The source is derived from the install, never from a request or a file; the target is replaced only when it is a real folder you own whose Info.plist names nika's bundle id; the copy is built in a temp sibling and swapped in with rename. Never `/Applications`, never sudo. `config.json` is validated on load; garbage falls back to defaults with a warning.
12. **Agent control.** `bypassPermissions` is refused at the store, API and spawn layers, for the Settings default and for each project's own `perProject.<key>.permissionMode` (0.4.0), and the mode switch never targets it (0.3; it may pass through it on the way to another mode when Claude's cycle holds it). Spawned agents get `--disallowedTools` for `Bash(nika:*)`, `Bash(tmux:*)`, `Bash(claude:*)`, `Bash(git add:*)`, `Bash(git commit:*)`, `Bash(git push:*)` and a deny list for `.env*` and `*.key`. **These lists are advisory, not a security boundary.** Claude Code matches permission rules against the literal command text, so `/opt/homebrew/bin/tmux …`, `sh -c 'tmux …'`, `git -C . commit` or a script written with Write and run with Bash all pass, and Read/Edit denies do not cover subprocesses. The lists stop the common invocation and honest mistakes; the boundary is the single-user trust model (constraint 10) plus the app secret. There is no Claude Code sandbox in 0.2; it is planned as an optional Settings switch (owner decision 2026-11-08). The guard prompt wording stays as is. Keystrokes go only to live Claude panes or nika-started panes, and only while the pane's current command looks like claude; text ≤ 1024 chars without controls, multi-line paste ≤ 16 KB only through tmux bracketed paste (`load-buffer -` + `paste-buffer -p -d`; only `\n` `\t` kept, ESC and every other control stripped), named keys from the allow-list in `src/ids.js`, ≤ 8 per request, 20 requests/s per pane. Session control (0.3, ADR 0010): Stop is its own route (`POST /api/app/pane/:id/stop`, outside the per-pane lock): only for a busy registry state with no prompt on screen it sends `Escape`, and when Claude's input is in vim insert mode (`-- INSERT --` shown) a second `Escape` only after the insert marker has gone and a state read that skips the registry cache still says busy; idle, no state or a prompt on screen send nothing (409). One interrupt runs per pane at a time, shared with End and kept apart from the lock (an overlapping Stop is 409 `stopping`, an overlapping End 409 `not-idle`, nothing sent). The keys route (the page's passthrough uses it too) refuses (409 `bypass-prompt`, nothing sent) a request with `Enter`, a digit in `text` or any `paste` while a permission prompt, or a dialog whose footer nika cannot read, with a window (the last 15 non-blank rows) that mentions bypass is on screen, after a fresh capture; only the terminal itself can answer such a prompt. End session takes a fresh capture; for a permission prompt on screen it sends `Escape` (the "No" path) and for a busy registry state it interrupts as Stop does, but with no registry state and no prompt it sends no key; it then waits 1 s and captures again; Claude still busy, a prompt still on screen, an unrecognized footer (a dialog may be open) or a non-empty input box refuses with 409 and types nothing; in vim normal mode it first types `i` and checks for `-- INSERT --`; it types `/exit` and presses `Enter` only when the input box then reads exactly `❯ /exit` (else it sends `C-u` to remove its own text and refuses), and reports `ended` only when the pane is gone or no longer runs claude within 3 s; nika never runs `kill-pane` and never signals a process. When nothing shows that vim is on, End and the quick-action commands type a command's first character `/` alone and read the screen (plain input: the rest follows; Claude's history search from vim normal mode: one `Escape`, then the `i` road; anything else, or a failed send of the rest: `/` removed, 409). A permission-prompt answer goes through a fresh capture and a signature check of the prompt rows (the page's `sig` must match), and only a digit among the shown options is typed; an option is never answered by nika when the prompt window, the option's label or its wrapped text mentions bypass. The mode switch runs only while Claude is idle (registry state `idle` and no permission prompt on screen), re-checked before every press; it presses `BTab` at most 6 times, re-reading the footer after each press, stops on an unrecognized footer, and runs one switch per pane at a time; its presses count toward the per-pane key limit; it never stops silently in bypass (while the footer last read bypass it presses without waiting for the registry, and any ending there is 409 `stopped-in-bypass`). Manual is reported only on Claude's positive footer marker, never by default. A brief never passes through tmux argv (`_run-agent` reads it from a 0600 file); it is claude's own argv, which any local process can read with `ps` (constraint 10). A brief must be more than one word (a lone word such as `update` could be read by claude as a subcommand), checked in the API, the CLI, the spawn sheet and `_run-agent`. The orchestrator's argv may carry `--resume <id>` for a stored pick and `--session-id <uuid>` for a fresh start; the id is a UUID checked at the store and the API, and must be a session of that project in nika's own index (a pick of another project's session is refused, and on Start treated as gone). **Auto-compact (0.4, ADR 0014).** When the `compaction` setting is on, every claude nika starts (the orchestrator, fresh or resumed, and spawned agents and sub-orchestrators) gets exactly two environment variables, `CLAUDE_CODE_AUTO_COMPACT_WINDOW` and `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` (both always, so an inherited value never stays in force), never the `--autocompact` flag. Their values come only from `compactLaunch` in `src/compact.js` (an integer window of 100000 to 1000000 and a percent string of digits and at most one dot, never null, computed from the model and the setting, never from a request, a file or Claude's settings); the orchestrator gets them as tmux `-e` pairs before `--` (after a `new-session` they are unset from the session environment again, constraint 3), and an agent through `compact` in `<name>.agent.json`, which `_run-agent` checks again (exact keys, same value rules, exit 3 on any mismatch) before adding the two variables to a copy of its own env for the `spawn()` of claude, with no shell. When the setting is off nika sets neither and the inherited environment goes through unchanged. nika never reads `autoCompactWindow` or any other key of a Claude settings file for this (constraint 4). **Nesting and limits (0.4, ADR 0013).** A main orchestrator may start sub-orchestrators (`role: orchestrator` in a spawn request, tagged `sub-orchestrator`), and a sub-orchestrator may start agents: three levels at most, never an agent under an agent. The parent comes from the page's `parent` pane id or from the CLI's `$TMUX_PANE` (no `--parent` flag), and the depth is computed from the parent's role in one fresh `tmux list-panes -a`; only this project's orchestrator and sub-orchestrators can parent, and any other pane nika tagged (an agent, another project's orchestrator or sub-orchestrator, a malformed or contradictory tag) is refused (409 `depth`); "you" is only no parent, a pane with no `@nika-role` at all, or the CLI's absent or unlisted `$TMUX_PANE`; the name `orchestrator` is reserved; and nothing is read from argv, env or a file. Every check that means "the main orchestrator" tests role `orchestrator`, so a sub-orchestrator is never taken for it. The agent limit N (the project's own `perProject.<key>.maxAgents` when set, else `limits.maxAgents`; 1 to 8, validated at the store) bounds the live agents and sub-orchestrators of one parent, and a project as a whole runs at most `min(3 × N, 24)`, checked first; a refusal is 409 `limit` with `{ scope, running, max }`. The duplicate-name check uses the same live set. The live set is the panes, in any tmux session, that tmux reports with `@nika-role` `agent` or `sub-orchestrator` and an `@nika-agent` tag `<project key>/<name>` for this project (set by nika when it creates the pane; the tag is parsed strictly, key must match `PROJECT_KEY` and name `AGENT_NAME`, anything else is ignored and never trusted; the name check compares the exact `<key>/<name>`), plus panes this process started. `<name>.pane` files are agent-writable and display only: they never count. A sub-orchestrator gets its own guard prompt and the agents' deny list, except that `Bash(nika:*)` is replaced by `Bash(nika)` and one `Bash(nika <command>:*)` for every CLI command other than `spawn` and `status`, generated from the CLI's command table so a new command is denied by default; this list is advisory like the agents' (see above). The CLI and the app server can race for the last free slot, so a cap can be exceeded by one pane (`docs/security.md` T36). nika never kills or owns agent processes.
13. **Desktop shell.** The webview navigates only to its own origin; `https://claude.ai/code/session_<id>` opens in the system browser via fixed argv (`open` / `xdg-open`); everything else is blocked and `window.open` is denied. No Tauri capability is granted to the server origin (no `window.__TAURI__`). The shell talks to the server only through the stdio JSON-lines protocol (`docs/contracts/api-app.md` §5). The page may ask the shell, through the server, to quit, close, minimize or zoom its window (a fixed `window` action list over stdio); on macOS the shell sets `ApplePressAndHoldEnabled` off in its own argument domain, in memory, so a held key repeats. The child runs with an env built from scratch (`env_clear`): `PATH`, `HOME`, `NIKA_APP=1` and, when set, `CLAUDE_CONFIG_DIR`, `NIKA_CONFIG_DIR`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`, `TMUX_TMPDIR`, `LANG`, `LC_ALL`, `LC_CTYPE`; nothing else is inherited, and `NIKA_NODE` only picks the node binary (it is not passed on). The shell finds node (0.3.2): a valid `NIKA_NODE` is the only candidate, else Homebrew, `/usr/local/bin`, on Linux Linuxbrew (`/home/linuxbrew/.linuxbrew`), `~/.local/bin`, `~/.volta/bin`, the newest mise, fnm (also under `~/Library/Application Support` on macOS), nvm and asdf install (found by listing their default folders) and `/usr/bin`, in that order (`docs/packaging.md`); the lookup runs on a worker thread, never the main one, and its answer is dropped if a newer start, an error page or Quit came first, and a lookup that ends without an answer (its thread panicked) shows the start-failed page, so Retry works; each existing candidate runs `node --version` with a fixed argv, a cleared env except `HOME` (the home the shell already uses; a Volta-style shim needs it), no shell, its own process group (a run that hangs is killed with whatever it forked, through `/bin/kill` with a fixed argv; so is the run still going when the app quits, and no further run starts then) and a 2 s limit, at most 6 s in total across candidates, spawn and read included, the kill after a timeout on top (then it decides with what it has read), and the first one that is 22 or newer is used; never the user's shell, a dotfile or a version-manager config file. No telemetry: the only outbound connection nika ever makes is the claude.ai link the user clicks (asserted by `test/hygiene.test.js`).

## Git

- Default branch `master` (never `main`), the only long-lived branch. Each change happens on a short-lived branch cut from `master` (`feat/…`, `fix/…`, `docs/…`, `release/X.Y.Z`) and reaches `master` only through a reviewed PR with all CI checks green, as a merge commit; merged branches are deleted (a PR page can restore one). Commits only with the owner's explicit approval per commit (ORCHESTRATION §19). No AI attribution lines.
- GitHub enforces this (owner decision 2026-11-09, repository rulesets): `master` takes changes only through a PR merged as a merge commit, with 1 approving review (a new push dismisses it; conversations resolved) and the six CI checks green from GitHub Actions (`node (macos-latest)`, `node (ubuntu-latest)`, `rust (macos-latest)`, `rust (ubuntu-22.04)`, `gui-smoke`, `linux-verify`) on a branch up to date with `master`; no deletion, no force push. Repository admins may bypass (the owner merges their own PRs with the bypass, since nobody can approve their own PR; GitHub logs each bypass), and a bypass is still a merge that needs the owner's approval. `v*` tags cannot be deleted or moved, with no bypass. Squash and rebase merges are off; head branches are deleted after a merge. A renamed CI job must be renamed in the ruleset in the same PR, or every PR stays blocked.
- Before each commit: `npm test` green (incl. hygiene) and `git diff master...HEAD` reviewed for paths, emails and ids.
- Publishing (repo creation, push, tags, releases, tap updates, CI workflow dispatch) needs the owner's approval for that specific action.
- Standing approvals (ORCHESTRATION §19) are recorded here with their date and branch, and end when that branch is merged. Active: `feat/0.4-fixes` (granted 2026-11-13) and the work branches of releases 0.5 and 0.6 (`feat/0.5-*`, `feat/0.6-*`, granted 2026-11-09); each ends when its branch is merged. Ended: `fix/0.2.0-release` and `feat/release-drafts` (both granted and merged 2026-11-08), `feat/0.3-session-control` (granted 2026-11-08, merged 2026-11-09), `fix/0.3.4-fixes` (merged 2026-11-09), `feat/0.4-orchestration` (merged 2026-11-13).
- Releases (owner decision 2026-11-08): pushing a tag `vX.Y.Z` makes `release-linux.yml` build the Linux packages and create a draft release; it never publishes. Pushing the tag, publishing the draft and updating the tap each need the owner's approval. Procedure: `docs/packaging.md`, Release procedure.
